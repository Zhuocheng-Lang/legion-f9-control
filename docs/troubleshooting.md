# 故障排查

`f9ctl` 把结果写到 stdout，把诊断写到 stderr，并且只显示一句话文案
（`f9ctl: <文案>`）；细节在 `f9d` 的日志里。排查时先看 `f9ctl` 的文案判断是哪一层，
再去启动 `f9d` 的终端（或 `journalctl`）找对应的一次请求。

错误文案由 `src/main.zig` 的 `messageFor` 集中生成；daemon 与 `f9ctl` 之间传的是
Zig 错误名（如 `AccessDenied`），文案只属于客户端，所以文案改动不影响通信格式。

## 1. 先确定是哪一层

| 现象 | 层级 | 下一步 |
| --- | --- | --- |
| `f9d 未运行（socket: …）` | 没有 daemon | §2 |
| `f9d: 启动失败: …` | daemon 启动阶段 | §3 |
| 其他 `f9ctl: …` 文案 | 设备链路 | §4 起 |
| 命令成功但数值可疑 | 设备状态 | §8 |

## 2. `f9d 未运行`

`f9d` 可以是 root 实例（`/run/f9d/f9d.sock`）或当前用户的开发实例
（`$XDG_RUNTIME_DIR/f9d.sock`）。客户端先试系统级路径，连不上再试用户级路径，
因此两台实例不会互相“顶替”，但也不应同时启动。

- 确认 `f9d` 进程在跑（`pgrep -a f9d`），并保持它在前台终端可见，才能看到日志。
- 以非 root 运行时报文案 `…（且未设置 XDG_RUNTIME_DIR，用户级 f9d 拒绝回退 /tmp）`：
  导出 `XDG_RUNTIME_DIR`（通常登录会话已自动设置）后重启 `f9d`。
- 报文案 `XDG_RUNTIME_DIR 过长，拼不出 f9d socket 路径`：把该变量换成短目录。
- socket 存在但没人监听（进程被 `kill -9`）：`f9ctl` 会把它当“未运行”处理；
  下次启动 `f9d` 时持锁后自动删除残留 socket。

## 3. `f9d: 启动失败: <错误名>`

运行目录相关的拒绝启动各有专门文案：

| 日志 | 原因 | 处理 |
| --- | --- | --- |
| `未设置 XDG_RUNTIME_DIR，拒绝回退到 /tmp（可预测路径有符号链接攻击风险）` | 非 root 且缺少该变量 | 导出 `XDG_RUNTIME_DIR` 后重启 |
| `XDG_RUNTIME_DIR 须为属主本人、权限不宽于 0700 的目录，拒绝启动` | 目录不属于当前用户或权限过宽 | `chmod 700 "$XDG_RUNTIME_DIR"`，或换用可信目录 |
| `XDG_RUNTIME_DIR 过长，socket 路径放不下，拒绝启动` | 路径超出系统上限 | 缩短 `XDG_RUNTIME_DIR` |

其余启动错误按 `f9d: 启动失败: <错误名>` 打印：

| 错误名 | 原因 | 处理 |
| --- | --- | --- |
| `AlreadyRunning` | `<socket>.lock` 已被另一个实例排他锁定 | 停掉旧实例；锁随进程退出自动释放，无需删文件 |
| `AccessDenied` | root 实例建不了 `/run/f9d` | 用 root 启动，或确认 `/run` 可写 |

非 root 实例对运行目录的要求是有意为之：可预测路径（如 `/tmp/f9d-<uid>.sock`）
能被同机其他用户占位，`f9d` 宁可拒绝启动也不回退。详见[架构与 IPC](design/0001-f9d-architecture-and-ipc.md)。

## 4. 找不到设备

- `未找到设备（USB 17ef:f00c 或 BLE 服务 UUID/LEGION_F9_BT）`：两条链路都没命中。
  确认设备已通电并插好；蓝牙场景还要确认设备处于可连接状态（未连到别的机器）。
  设备晚于 `f9d` 启动接入是允许的——句柄在第一次请求时惰性打开，无需重启 daemon。
- `USB 设备存在但协议接口无应答`：设备枚举成功，但协议接口在 300ms 探测窗口内没回。
  同一 VID:PID 会枚举出多个 hidraw 节点（键盘/消费者控制/协议接口），
  daemon 按顺序探测并跳过无应答的节点。若所有节点都无应答，先拔下重插；
  仍复现请附上 `lsusb -v -d 17ef:f00c` 与 `dmesg` 相关行。

只有“未找到设备”和“无应答”会用蓝牙兜底；权限与 I/O 错误直接上报，不会被蓝牙掩盖。

## 5. 权限问题

- `无权限访问设备或 BlueZ（hidraw 需 root 或 udev 规则；BLE 需能连 system bus）`：
  - USB：`/dev/hidraw*` 默认只有 root 可读写。可 `sudo` 启动 `f9d`，
    或为自己写 udev 规则（`uaccess`/`MODE`）后以本人身份启动。
  - 蓝牙：需要用 system bus（`/run/dbus/system_bus_socket`）访问 BlueZ。
- 权限错误**不会**触发蓝牙兜底：请修权限，而不是换链路。

## 6. 超时与断线

| 文案 | 含义 |
| --- | --- |
| `等待响应超时` | 本次请求在预算内没有拿到有效响应，且未触发会话收尾 |
| `设备不存在，可能已拔出` | 拔线（`ENODEV`/`EPROTO`/EOF 等）或节点消失 |
| `设备 I/O 错误，可能已拔出` | hidraw 读写返回 `EIO` |
| `BLE 设备未连接或链路中断` | 连接已被 BlueZ 断开 |
| `f9d 提前关闭了连接` / `与 f9d 通信的报文超长` | IPC 层异常，通常是 daemon 崩溃或版本不一致 |

预算（见[架构与 IPC](design/0001-f9d-architecture-and-ipc.md)）：USB 单次事务 2s；
BLE 打开（扫描 + 连接 + 服务解析）12s、单次操作 5s、整请求 30s；`f9ctl` 等 IPC 35s。
因此设备断电时，一次请求可能在十几秒后才报错——这是有界失败，不是卡死。

失败后 `f9d` 丢弃句柄，下个请求重新建链；不会在同一请求内换链路，也不会重放写入
（挡位以最后提交的值为准）。

`等待响应超时` 目前也用于 BLE 的连接/服务解析阶段，文案容易被误读为客户端等待超时，
语义收缩已列入[后续计划](ROADMAP.md)的“待定夺”项。

## 7. 设备返回的状态不是成功

- `设备忙（状态 0xfe）`：设备正在处理上一条命令（例如刚写完挡位），稍后重试。
- `设备返回错误（状态 0xff）`：设备拒绝了本次命令，先确认挡位值合法。
- `响应状态字节未知`：状态字节不在 `0x00/0xfe/0xff` 里，多为主机侧解析错位，
  请附上 `f9d` 日志与复现命令。
- 帧校验类文案（`响应帧长度异常`、`响应 report ID 异常`、`响应命令回显不匹配`、
  `响应数据过短`、`BLE 响应帧头（0xee）异常`、`BLE 响应声明长度与请求不符`、
  `BLE 响应偏移与请求不符`）：
  说明收到的帧不属于本次请求。USB 的 report 节点是多路复用的，设备会主动推送
  短通知，正常情况下这类帧会被丢弃；能报到 `f9ctl` 说明真的收到了不符的响应。
  请记录复现步骤与 `f9d` 日志，不要为提高兼容性放松校验。

## 8. 挡位设置失败或数值异常

- `设置后回读的挡位与请求不一致`：写入后回读到的挡位不是请求值。挡位以回读为准，
  失败不会当成功返回；重试一次通常即可，反复出现请记录 `f9d` 日志。
- `设置块中的挡位值无效` / `无效挡位（quiet/balanced/beast/turbo 或 0-3）`：
  后者是本地参数错误（在连 daemon 之前就拒绝），前者是设备上的设置块内容不是已知挡位值。
  设置块除挡位外的字节会被原样写回，固件改动导致布局变化时会出现该错误。
- `响应数据过短`：读设置块不足 15 字节，多为链路问题，按 §6 处理。
- 转速显示为 `0`：`rpm = rpm_raw >> 2`，设备报告 `rpm_raw` 为 0 时就是 0；
  `flag`/`rpm_raw` 的字段含义见[硬件协议](spec/0001-legion-f9-protocols.md)。
  v1 只读取 flag 与转速，协议中没有温度字段，`f9ctl` 也不输出温度。

## 9. 蓝牙专项

- `BlueZ 不可用（system bus 未运行、无蓝牙适配器或蓝牙未启用）`：
  `systemctl status bluetooth`；确认适配器未 `rfkill` 关闭。
- `设备缺少目标 GATT 服务/特征，或写特征不支持 write-with-response、通知特征不支持 notify`：
  设备固件与协议不符，或连到了同名的其他设备。本工具不去枚举/猜别的 UUID。
- `BlueZ D-Bus 调用失败（细节见 f9d 日志）`：`f9d` 日志里有具体的方法名与错误。
- 蓝牙地址会变化，日志只记错误名、不打印设备路径；排查时不必、也不要收集地址。
- 同时存在两台同类设备时，服务/特征只从选中的设备内采纳；若怀疑选错，
  让另一台断电后再试。

## 10. 提交问题前

请附上：`f9ctl` 的完整 stderr 文案、`f9d` 同一次请求的日志、连接方式（USB/蓝牙）、
发行版与内核版本，以及 `mise exec -- zig version` 的输出。不要附设备地址、
抓包数据或其它私有材料。仍未做真机验收的场景见[验收记录与后续计划](ROADMAP.md)。
